# Reglas de trabajo para Claude en este repositorio

Este archivo gobierna cómo debo (Claude) trabajar en este proyecto. Se aplica a toda sesión futura, no solo a la actual.

## Fuente de verdad

1. **`docs/arquitectura-banca-digital-bp.md`** es la fuente de verdad de las decisiones de arquitectura (stack, patrones, servicios AWS). Ninguna decisión de esa lista se cambia "sobre la marcha" al programar: si el código exige desviarse de una decisión, se detiene el trabajo, se explica el conflicto al usuario y se actualiza el documento primero.
2. **`CHECKLIST.md`** es la fuente de verdad de qué falta por construir y en qué orden.
3. **`WORKLOG.md`** es la fuente de verdad de qué se hizo realmente y cómo se verificó.
4. **`README.md`** es la fuente de verdad de cómo levantar el proyecto de cero (requisitos previos + pasos de instalación/arranque) para cualquiera que clone el repo, en local o en un servidor. Es la única de las cuatro pensada para un lector externo, no para gobernar el propio trabajo de desarrollo.

Antes de tocar código en una sesión nueva: leer `CHECKLIST.md` (qué sigue) y las últimas 2-3 entradas de `WORKLOG.md` (qué se hizo y qué quedó pendiente).

## Disciplina de avance (regla central)

- Se trabaja **un ítem del checklist a la vez**, en orden, respetando las dependencias entre fases.
- Un ítem se marca `[x]` **solo** cuando está implementado y verificado (build/lint/test corridos y en verde, no solo "el código parece correcto"). Si algo no se puede verificar automáticamente, se dice explícitamente cómo se verificó manualmente.
- No se avanza al siguiente ítem con el anterior a medias. Si aparece un bloqueo, se marca `[!]` en el checklist, se registra el motivo en `WORKLOG.md`, y se pregunta al usuario en vez de improvisar una solución que se desvíe de la arquitectura.
- Si durante el desarrollo aparece trabajo no previsto (una dependencia faltante, un ajuste de diseño), se agrega como ítem nuevo al checklist en vez de hacerlo "silenciosamente" y seguir de largo.
- Al cerrar un ítem (o un grupo pequeño de ítems relacionados de la misma fase), se agrega la entrada correspondiente en `WORKLOG.md` **antes** de pasar al siguiente ítem.
- No completar fases enteras sin pausar: al terminar una fase completa del checklist, resumir al usuario lo hecho y esperar confirmación antes de iniciar la siguiente fase.
- **Ninguna fase se da por cerrada sin actualizar `README.md`.** Si la fase agrega algo que alguien necesitaría para levantar el proyecto en una máquina limpia (un nuevo servicio, una nueva variable de entorno, un nuevo comando, un nuevo requisito previo como una versión de lenguaje o una herramienta), eso tiene que quedar reflejado en la sección de instalación del README en el mismo commit que cierra la fase — no después, no "cuando se acuerde". El README debe poder seguirse de punta a punta por alguien que nunca vio el proyecto, sin tener que adivinar pasos a partir del código o del checklist.

## Convenciones técnicas del proyecto

**Backend (Laravel, PHP 8.3+):**
- Un microservicio = una app Laravel independiente bajo `services/<nombre>`, con su propio `composer.json`, `Dockerfile` y `.env.example`.
- En cada servicio, fijar `"config": {"platform": {"php": "8.3.99"}}` en `composer.json` (y commitear su `composer.lock`). Sin esto, `composer install/update` resuelve versiones según el PHP del host de quien lo corra — si el host tiene un PHP más nuevo que el 8.3 de la imagen Docker (pasó con `svc-customer-data`: host 8.5, imagen 8.3), el lock queda con paquetes que no instalan dentro del contenedor.
- Código compartido entre servicios va en `packages/bp-common` (paquete Composer local vía path-repository) — nunca se copia/pega middleware o utilidades entre servicios. Los helpers de testing reutilizables entre servicios (como `RsaKeyPair`/`FakeJwksProvider` para firmar JWTs de prueba) van en `packages/bp-common/src/Testing/` (autoload normal), no en `tests/` del paquete (autoload-dev no es visible para otros consumidores).
- El `Dockerfile` de cada servicio se construye con el **contexto en la raíz del monorepo**, no en la carpeta del servicio, porque necesita copiar `packages/bp-common` (dependencia local vía path-repository): `docker build -f services/<nombre>/Dockerfile -t bp/<nombre> .`
- Ningún ítem de checklist que agregue un `Dockerfile` se marca `[x]` sin haber corrido `docker build` (y, si expone HTTP, `docker run` + un curl real) — un Dockerfile que "se ve bien" pero no se construyó no cuenta como verificado.
- Estilo de código: PSR-12, aplicado con Laravel Pint antes de dar por cerrado cualquier ítem de backend.
- Cómputo pensado para Octane (Swoole): evitar estado mutable en propiedades de clases que Octane mantiene vivas entre requests (singletons, estáticos) salvo que sea intencional.
- Cualquier integración externa (DynamoDB, EventBridge/SQS, S3, Auth0, KYC, red interbancaria, Pinpoint/SES) se escribe contra una **interfaz** (Repository/Adapter). Cada interfaz tiene como mínimo un driver `local` (mock/fake/LocalStack) y un driver real, seleccionados por variable de entorno — nunca un `if (app()->environment('local'))` disperso en la lógica de negocio.
- MySQL es real desde el día 1 (no se mockea): es el mismo protocolo que Aurora MySQL en producción, así que promoverlo a AWS es solo cambiar host/credenciales.
- DynamoDB (local vía LocalStack, real en AWS) usa el `DynamoDbClient`/`Marshaler` ya registrados como singleton en `bp-common` (`bp-common.dynamodb.*` por `.env`) — no crear un cliente nuevo por servicio. Ojo: `Marshaler::unmarshalItem()` deserializa un `Number` sin parte decimal como `int` en vez de `float` (ej. `30` en vez de `30.0`); si el campo es un monto u otro decimal, forzar `(float)` explícitamente al leerlo (visto en `svc-movements`, aplica también a la auditoría en DynamoDB de la Fase 5).
- El bus de eventos usa el `EventPublisherInterface`/`EventBridgeEventPublisher` de `bp-common` (`bp-common.events.*` por `.env`) — no reimplementar la publicación a EventBridge en cada servicio. En local, el bus de EventBridge (`bp-domain-events`) y cualquier tabla DynamoDB que un servicio necesite no existen solos: cada servicio que los use debe traer su propio comando artisan idempotente de provisión (ver `movements:setup-table` / `events:setup-bus` en `svc-movements` como referencia) y documentarlo en su sección del README.
- Todo servicio expone `GET /health` (del paquete `bp-common`) y valida JWT con el middleware compartido. **Excepción:** los servicios "worker puro" que solo consumen SQS (Auditoría, Notificaciones) no sirven HTTP y por lo tanto no necesitan Octane/Swoole ni exponen ese `/health` — su Dockerfile corre directo el comando de consumo como proceso principal.
- Un servicio descrito en la arquitectura como "Laravel Horizon Worker" no siempre implica usar Horizon en sentido estricto: Horizon supervisa la cola *interna* de Laravel (Redis/database); si la fuente real de trabajo es una cola SQS con el sobre de EventBridge (no un job de Laravel), el patrón correcto es un comando Artisan de larga duración que hace long-polling directo contra el SDK de AWS (ver `audit:consume` en `svc-audit`, con una opción `--once` para poder probarlo sin loop infinito). Aplica igual para Notificaciones en la Fase 6.
- Un comando/worker que consume mensajes de una cola nunca debe quedar en silencio total al terminar de procesar uno con éxito — si solo loguea en el `catch`, un "no pasó nada" es indistinguible de un "no llegó nada". Loguear explícitamente tanto el éxito como el error.
- Cada servicio commitea su `.env.example`; el `.env` real siempre va en `.gitignore`.

**Entorno local (Docker):**
- El entorno de infraestructura se maneja con `make up` / `make down` / `make logs` / `make ps` (nunca `docker compose` directo salvo para depurar), para que el flujo sea el mismo sin importar cuántos servicios se agreguen. Desde la Fase 11, `make dev` (y `dev-down`/`dev-logs`/`dev-ps`/`dev-restart`) levanta infraestructura + los 7 servicios backend con `docker compose --profile services ...` — `make up` a secas sigue siendo **solo infraestructura**, el flujo de las Fases 2-10 no cambió.
- Si una imagen Docker de terceros crashea en bucle en esta máquina (Apple Silicon) con errores que huelen a incompatibilidad nativa (p. ej. `FileLoadException` de .NET, "exec format error"), probar primero fijando `platform: linux/amd64` en el servicio antes de buscar otra imagen — resolvió el caso de `oidc-server-mock`.
- Al levantar varios servicios a la vez con comandos encadenados (`cd servicio-a && php artisan serve ... &` seguido de otro `cd servicio-b && ...`), el directorio de trabajo del shell persiste entre llamadas de la herramienta Bash **aunque el comando se haya lanzado en segundo plano** — si el siguiente comando no vuelve a hacer `cd` explícito a su propio servicio, arranca en el directorio equivocado. Se detectó en la Fase 7 porque cada `/health` imprime el nombre de su propio servicio: verificar siempre el *contenido* de `/health` al levantar varios procesos juntos, no solo el código de estado 200.
- **Un contenedor no puede alcanzarse a sí mismo por "localhost" desde otro contenedor** (Fase 11): al mover un servicio de "corre en el host" a "corre en la red de docker-compose", cualquier URL que apuntara a `localhost:<puerto>` de OTRO servicio tiene que pasar a usar el nombre del servicio de compose (`mysql`, `redis`, `localstack`, `mock-oidc`, `svc-customer-data`, etc.). El caso más sutil es el emisor OIDC: el `iss` de un token real sigue siendo `http://localhost:4011` (así lo ve el navegador al loguearse) y ESO no cambia, pero el proceso que valida el token dentro de un contenedor necesita una URL *distinta* (`http://mock-oidc:80`) para bajar el JWKS — ver `OIDC_DISCOVERY_ISSUER` en `JwtValidator`/`bp-common.php`. No asumir que "el mismo valor sirve para todo" solo porque en el host coincidían.
- Los contenedores de este proyecto **no tienen archivo `.env`** (excluido vía `.dockerignore` en la raíz) — toda su configuración viene de `environment:` en `docker-compose.yml`. Esto es intencional (nunca hornear un `.env` local dentro de una imagen) pero implica que cualquier variable que un servicio necesite y que NO tenga ya un default sensato en su propio `config/*.php` hay que declararla explícitamente en `docker-compose.yml` — no alcanza con que exista en `.env.example`, ese archivo no se lee dentro del contenedor.
- Un `Dockerfile` de un servicio con lógica de negocio que corre migraciones o comandos de provisión (idempotentes) debe hacerlo en su propio `CMD` de arranque (`sh -c "php artisan migrate --force && ... && php artisan octane:start ..."`), no como un paso manual aparte — así un solo `docker compose up`/`make dev` deja todo listo. Un servicio con base de datos SQLite además necesita `touch database/database.sqlite` antes de migrar, porque ese archivo (si existía) está en `.gitignore` y no llega al build context de una máquina que recién clonó el repo.
- **Un `docker build` local puede tener extensiones de PHP que la imagen no tiene** (Fase 11): los tests de un servicio corridos en el host pueden pasar en verde durante meses sin que nadie note que al `Dockerfile` le falta una extensión (pasó con `bcmath`/`bccomp()` en `svc-transfers` — el PHP del host la trae por defecto, la imagen Docker no, y nadie había ejecutado una transferencia real *dentro* del contenedor hasta la Fase 11). La única forma de detectar esto es ejercitar el camino de negocio real dentro del contenedor (no alcanza con que `docker run` responda `/health`) — por eso el criterio de aceptación de la Fase 11 exige login + movimientos + transferencia real de punta a punta, no solo que los contenedores levanten.
- Un middleware que "cachea la respuesta de la request anterior" (como `IdempotencyMiddleware`) nunca debe asumir el tipo concreto de lo que devuelve `$next($request)` (ej. llamar `->getData()` asumiendo `JsonResponse`) — un error no controlado más abajo en la pila puede producir una respuesta genérica (`Illuminate\Http\Response`) que no tiene ese método, y el `BadMethodCallException` resultante oculta el error real. Verificar `instanceof JsonResponse` antes de tratarla como tal.
- Un mock de OIDC self-hosted (`soluto/oidc-server-mock`) sin un API Resource/Scope configurado emite access tokens **sin `aud`** (solo `client_id`) — si `JwtValidator` exige un audience, hay que declarar `API_SCOPES_INLINE`/`API_RESOURCES_INLINE` en el mock y pedir ese scope explícitamente desde el cliente, igual que se declararía un audience contra un tenant real de Auth0/Okta. Su formulario de login (`/Account/Login`) además exige un campo de botón con nombre (`Input.Button=login`) además de usuario/contraseña/CSRF token — sin él, el login "parece" funcionar (devuelve 302) pero nunca autentica y el flujo termina en `error=access_denied` sin pista clara de por qué.
- Una cola SQS de LocalStack con `PERSISTENCE: 1` acumula mensajes indefinidamente entre reinicios — un test que publica un evento y espera consumirlo con `--once` puede fallar de forma intermitente si la cola ya tiene un backlog grande de pruebas manuales anteriores (el consumidor agarra mensajes viejos en vez del recién publicado). Si un test así falla sin que el código haya cambiado, purgar la cola (`SqsClient::purgeQueue`) antes de sospechar de una regresión real.

**Frontend (React + TypeScript / React Native + TypeScript):**
- ESLint + Prettier obligatorios, sin warnings bloqueantes al cerrar un ítem. **Adaptación (Fase 9):** el scaffold actual de `npm create vite@latest -- --template react-ts` trae `oxlint` (linter Rust, reglas compatibles con ESLint/React/TypeScript) en vez de ESLint clásico — se usa `oxlint` como reemplazo funcional de esa regla, no se reinstala ESLint clásico encima. Prettier se mantiene igual.
- El `tsconfig` de ese mismo scaffold trae `erasableSyntaxOnly: true`, que prohíbe *parameter properties* de TypeScript (`constructor(public readonly x: T) {}`) porque generan código no "erasable" en tiempo de compilación — declarar las propiedades explícitamente y asignarlas en el cuerpo del constructor (visto en `BffError` de `frontend-web`).
- Lógica de negocio compartible entre SPA y móvil (validaciones, formateo, llamadas a API) se aísla en módulos reutilizables, no se duplica entre ambos proyectos.
- Nunca se hardcodea la URL de un BFF ni el modo de OAuth: todo por variables de entorno (`.env` / `.env.local` según el bundler), con su `.env.example`.
- El `client_id` y `redirect_uri` de OAuth de cada frontend deben coincidir exactamente con los ya registrados en `CLIENTS_CONFIGURATION_INLINE` de `mock-oidc` (`docker-compose.yml`) — ahí ya está preconfigurado un cliente público `bp-web` con PKCE obligatorio y `redirect_uri` `http://localhost:5173/callback` (SPA) y `http://localhost:19006/callback` (reservado para la app móvil/Expo, Fase 10). No inventar un `client_id` nuevo sin agregarlo también a esa configuración.
- Sin navegador disponible en este entorno, un flujo OAuth se puede verificar de forma real (más allá de tests unitarios) construyendo a mano la URL de `/connect/authorize` con los mismos parámetros que generaría la librería del cliente (`client_id`, `redirect_uri`, `code_challenge`/`code_challenge_method=S256` para PKCE) y confirmando con `curl` que el emisor OIDC la acepta sin `invalid_client`/`invalid_scope` y redirige a su propia pantalla de login — no reemplaza un click real, pero prueba que el cableado (cliente registrado, redirect_uri, scopes, PKCE) es correcto de punta a punta.
- **Sin Xcode Simulator/Android SDK disponibles en este entorno (Fase 10):** para React Native/Expo, el equivalente al chequeo de `npm run dev` de la SPA es `npx expo start --web` (react-native-web) — sirve para confirmar que Metro bundlea sin error y que las variables `EXPO_PUBLIC_*` se inlinean bien, pero requiere `react-dom`/`react-native-web` instalados aparte (`npx expo install react-dom react-native-web`, no vienen en el scaffold `blank-typescript`). Cualquier módulo nativo sin implementación web (`expo-local-authentication`, `expo-secure-store`) tiene que guardarse detrás de un chequeo `Platform.OS === 'web'` en el propio código para no romper ese smoke test — no alcanza con que la librería tenga un stub que lance error, hay que evitar invocarlo.
- El scaffold de Expo (`create-expo-app`) trae su propio `AGENTS.md`/`CLAUDE.md` avisando que el SDK instalado "cambió" respecto a lo que un LLM pueda recordar y a consultar `docs.expo.dev/versions/v<version>` antes de escribir código — tomarlo en serio: las APIs de `expo-auth-session`/`expo-local-authentication`/`expo-secure-store`/`expo-crypto` cambian de una versión de SDK a otra.
- `react-test-renderer` debe fijarse a la MISMA versión exacta que `react` (no `^`/`latest`) — son un par acoplado 1:1; `npm install` con `latest` puede resolver una versión de `react-test-renderer` que exige un `react` más nuevo que el que fija el SDK de Expo, y falla con `ERESOLVE`.

**Tests de frontend (Vitest + React Testing Library / Jest + React Native Testing Library):**
- Cuando un mock de función (`vi.fn()`/`jest.fn()`) se define a nivel de módulo (dentro de `vi.mock(...)`/`jest.mock(...)`) y se usa en varios `it()` del mismo archivo, resetear sus llamadas/implementaciones encoladas en `beforeEach` con `mockReset()` — si no, los conteos de llamadas y los `mockResolvedValueOnce`/`mockRejectedValueOnce` de un test se filtran al siguiente (pasó en `TransferPage.test.tsx`: un test veía 3 llamadas acumuladas donde esperaba 2, arrastradas del test anterior). `mockClear()` no alcanza porque no vacía la cola de implementaciones `Once` pendientes de un mock ya consumido a medias.
- `jest-expo` ya trae extendido `expect` con los matchers de `@testing-library/react-native` (`toBeDisabled`, `toHaveTextContent`, `toBeOnTheScreen`, etc.) — no hace falta un `setupFilesAfterEach` a mano para eso (se probó y sobraba).
- Dentro de un `jest.mock(...)`, el factory no puede leer variables de módulo salvo que su nombre empiece con `mock` (case-insensitive) — un contador para generar UUIDs falsos en el mock de `expo-crypto`, por ejemplo, tiene que llamarse `mockUuidCounter`, no `uuidCounter`, o Jest tira `ReferenceError`.

**Backend — errores de servicios internos hacia BFFs (bp-common):**
- `UpstreamServiceException` (en `packages/bp-common/src/Clients/`) preserva el `errorCode` de negocio del servicio interno (ej. `step_up_required` de `StepUpAuthMiddleware`), no solo el mensaje y el status code — `HandlesUpstreamErrors::upstreamError()` lo usa en vez de aplanar siempre a `"upstream_error"`. Un frontend que necesite reaccionar a un código de negocio específico (no solo mostrar el mensaje) debe leer `error.code` del envelope, nunca parsear el texto del mensaje (se encontró y corrigió un caso así en `TransferPage.tsx` durante la Fase 10 — llevaba desde la Fase 9 detectando el step-up por substring del mensaje).
- Ojo con nombrar una propiedad `code` en una excepción PHP: `Exception::$code` ya existe en la clase base y NO es `readonly` — redeclararla como `readonly` en una subclase (parameter property de PHP 8) revienta con `Fatal error: Cannot redeclare non-readonly property as readonly`. Usar otro nombre (`errorCode`, `businessCode`, etc.).

**Pruebas:**
- Ningún ítem de checklist que agregue una regla de negocio (idempotencia, compensación de Saga, invalidación de caché, apertura de Circuit Breaker, etc.) se marca `[x]` sin al menos un test automatizado que la ejerza.
- Los tests corren contra la infraestructura local (`docker compose`), nunca contra servicios reales de AWS o proveedores externos.
- MySQL se limpia solo entre tests con `Illuminate\Foundation\Testing\DatabaseTransactions` (cada test corre en una transacción que se revierte al final). **Redis no se revierte solo** — cualquier test que escriba estado compartido en Redis con una clave fija (locks, contadores de Circuit Breaker, etc., no claves con un id único por test) tiene que limpiarlo explícitamente en `tearDown()`, o contamina al siguiente test que use la misma clave (pasó en `svc-transfers` con el estado del Circuit Breaker). Cuando la clave sí incluye un identificador único por test (un `cuentaId` con UUID, por ejemplo), no hace falta limpieza porque no hay colisión posible.

**Seguridad:**
- Nunca commitear secretos, tokens o credenciales reales — solo valores de ejemplo en `.env.example`.
- Antes de un `git add` amplio, revisar que no se cuele un `.env` real ni credenciales de prueba con aspecto de reales.

## Git y control de versiones

- Nunca crear commits ni hacer push sin que el usuario lo pida explícitamente para esa tanda de cambios (regla general ya vigente en este proyecto, no específica de código).
- Mensajes de commit en español, estilo conventional commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`), describiendo el *por qué* del cambio, no solo el qué.
- No usar `--force`, `--no-verify` ni reescritura de historia sin pedirlo explícitamente el usuario.

## Comunicación con el usuario

- Ser explícito sobre qué fase/ítem del checklist se está trabajando en cada momento.
- Si una decisión de la arquitectura resulta poco práctica al implementarla (por ejemplo, una limitación real de LocalStack o de Octane), decirlo y proponer alternativa — no decidir en silencio.
- Resúmenes de fin de turno: qué ítems quedaron en `[x]`, cuáles en progreso, y cuál es el siguiente paso concreto.
